# Docling 검수

원본 PDF는 증거, 변환 결과는 해석 가설, 리치오 문서는 검증된 결과로 다룬다. 교정 대상은 리치오 문서다. 변환 JSON을 패치하거나 재변환해 검수 기록을 대신하지 않는다.

## 검사 흐름

1. 사용자가 지정한 문서·검수 작업공간 경로로 `read_review_document`를 호출해 현재 대상과 상태를 읽는다. 대상이 모호하면 사용자에게 경로를 확인한다.
2. `read_review_material`로 렌즈, 필수 확인 목록, 기존 묶음과 원문 증거 후보를 읽는다. 후보가 없거나 새 검사가 필요하면 `run_review_source_evidence`로 후보를 만든다. 후보는 오류 확정이나 교정안이 아니다. 숫자·단위 불일치 후보부터 확인하고, 후보에 없는 구조·읽기 순서·수식·표·그림·장식 렌즈도 실제 요청 범위에 맞춰 검사한다.
3. 의심되는 쪽의 자료를 `read_review_material`로 읽는다. 이웃 항목·관계·원문/좌표·현재 문서 대응을 함께 보고 국소적으로 판단한다. 그림·표의 필수 확인과 추출 실패/지원 불가 영역은 텍스트가 있다는 이유만으로 검사 성공으로 간주하지 않는다.
4. 증거가 충분한 차이만 `propose_review_groups`로 국소 교정 묶음에 저장한다. 현재 문서의 교정 전 값과 원본 근거를 연결하고, 서로 독립적으로 판단할 수 있는 문제는 나눈다. 화면에 보이지 않는다는 이유로 글자를 삭제하지 않는다. 번호만 보고 제목 수준을 바꾸거나 표의 빈 칸·없는 블록을 추측해 채우지 않는다. 삽입은 실제 원문 증거에 근거한다. 확실하지 않은 차이는 교정안을 꾸미지 말고 판단 불가로 남긴다.
5. `record_review_inspection`으로 실제 읽은 쪽·대상·렌즈 범위만 기록한다. 문제 없음, 문제 발견, `uncertain`을 구분한다. 자료가 부족하거나 읽지 못한 범위는 `uncertain`으로 남기며, 후보 목록만 읽은 것을 모든 쪽 검사로 확대하지 않는다. 기록은 승인·필수 확인 완료·문서 전체 검수 완료를 대신하지 않는다.
6. 이미지 대조가 필요하면 `estimate_review_images`로 필요한 쪽 또는 영역의 예상량을 구하고, 반환된 선택과 estimateHash를 그대로 담아 `request_litzio_user_input`의 reviewImage 질문 카드로 사람의 승인을 받는다. 질문 접수는 승인이 아니다. 실제 사람 답변의 runId를 받은 뒤 승인된 범위만 `read_review_images`로 읽고 검사 기록을 보완한다. 이미지가 없거나 승인 범위를 다 읽지 못했으면 대조 완료로 기록하지 않는다.

## 저장과 인계

검수 쓰기의 응답이 불확실하면 같은 요청의 `read_review_request_status`를 조회한다. 새 요청을 만들어 같은 쓰기를 재시도하지 않는다. 거부된 입력·권한·대상을 shell이나 CLI로 우회하지 않는다.

비서는 제안과 검사 기록까지만 맡는다. 묶음의 승인·거절·Undo·완료는 사람이 제품 화면에서 처리한다. 보고에는 검사한 범위, 제안한 문제, 판단 불가와 남은 필수 확인을 구분한다. 전수 검사를 하지 않았으면 전체 검수가 끝났다고 말하지 않는다.
