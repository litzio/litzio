# 표 커서 도구 배치 스파이크 (#1481)

결론: 미정. 소유자의 시각 검토 뒤 구현 여부를 정한다. 이 브랜치는 제품 구현 PR로 병합하지 않는다.

## 질문과 만든 것

표 도구를 위한 빈 공간을 읽기 전용 수준으로 줄이고, 커서가 표 안에 있을 때만 현재 행·열 손잡이와 가장자리 추가 막대를 띄워도 글자와 겹치지 않고 문서 높이가 유지되는가?

`index.html`은 1440px의 현재/시안 나란한 비교다. 밝은/어두운 테마 각각 커서 밖, 커서 안, 행 메뉴, 글자가 많은 6개의 좁은 열, 본문 폭을 채운 표, 1200px 가로 스크롤 표를 포함한다. `prototype/`에 합성 문서·재현 본문(CSS 포함)·24 PNG·측정 JSON을 보존한다. 개인 참고 이미지는 포함하지 않았다.

## 결과와 판단

- 보통 표: 현재 211px → 시안 135px (76px 감소). 시안의 커서 밖/안/행 메뉴 모두 135px. 고정 overlay라 도구 등장이 flow에 공간을 더하지 않는다. 시각 시안의 높이 비교이며 브라우저 수락 검증이 아니다.
- 커서 밖은 도구 0개, 안은 현재 행/열 손잡이와 아래/오른쪽 막대 4개, 메뉴 중은 손잡이 2개만 남는다. hover만으로는 표시하지 않는 것을 추천한다. 표를 읽다가 포인터가 지나갈 때 생기는 잡음을 줄이고 커서 기준을 일관되게 한다. hover-only 별도 수락 검사는 하지 않았다.
- 손잡이의 보이는 면은 기존 compact token(28px)의 긴 축과 space-3(12px) 짧은 축을 기준으로 했다. 위 손잡이는 표 테두리에 6px씩, 왼쪽도 6px씩 걸친다. 색은 기존 surface/text-muted/border 역할을 재사용했다. 아래/오른쪽 막대는 space-2(8px), 바깥 간격 space-1(4px). 구현에서는 이 시각 면과 별개로 기존 접근성 hit target 기준을 지켜야 한다.
- 꽉 찬 6열 머리글의 DOM Range와 시안 버튼 교차는 0이었다. 두 테마에서 셀 글자를 덮지 않는 것을 PNG로 확인했다. 이전 넓은 열 손잡이처럼 머리글 폭 전체를 덮지 않는다.
- 아래 막대는 캡션 다음 4px에 둔다. 표 아래 캡션을 보존하는 리치오의 조건 때문에 그리드 바로 밑이 아닌 전체 caption-inclusive table 아래다. 블록 사이 여백에 겹쳐 그리며 본문 높이를 늘리지 않는다.
- 오른쪽 막대는 전체 표 실제 오른쪽 끝이 아닌 **가로 스크롤 viewport의 오른쪽 바깥 4px**에 붙인다. 1200px 표를 오른쪽으로 스크롤해도 보이며 마지막 열 뒤 추가라는 기존 명령을 유지한다. 전체 높이는 캡션 포함이다. 스크롤 내부에 두면 잘리는 문제가 있어 시안에서는 body overlay로 배치했다.
- 가로 스크롤 중 왼쪽 손잡이는 viewport 바깥에 완전히 둔다(왼쪽 14px, 폭12px). 원시 Range 측정은 잘려서 보이지 않는 `Long identifier 04` 범위와 0.78×18px 교차를 기록했다. 실제 viewport 안 글자를 덮는다는 증거로 해석하지 않는다. clipping-aware hit test는 구현 때 필요하다.
- 오른쪽 여백이 12px도 없으면 막대 대신 현재 열 메뉴의 기존 ‘열 추가’를 사용하고 막대만 숨기는 대안을 추천한다. 안쪽으로 옮겨 글자나 스크롤바를 덮지 않는다. 이번 1440px 표본에는 바깥 여백이 있었으며 이 대안을 별도 시안으로 만들지는 않았다.
- 기존 블록 손잡이는 더 왼쪽, 현재 행 손잡이는 테두리에 있어 물리적으로 구별된다. 첫 행에 커서가 있을 때 두 점 아이콘이 가까이 보여 혼동 가능성은 남는다. 전체 표/행 tooltip·포커스 이름과 포인터 target 검증이 필요하다.

## 시안의 한계와 현재 계약과 다른 점

제품 파일을 변경하지 않았다. 검사 본문이 현재 DOM의 버튼을 복제해 고정 overlay를 그리며 원래 버튼 click에 연결한다. 메뉴 항목과 Core 명령은 기존 것을 썼다. 행 메뉴를 여는 동안 전체 행 강조는 CSS 표시이며 엔진의 실제 RowSelection 구현이 아니다. 스크롤·resize·커서 이동을 계속 추적하는 제품 수명, 키보드 discovery/parity, 저장/Undo는 이번 배치 검토의 검증 범위가 아니다.

기존 `table-interaction-v1.md`의 editable 도구 자리 상시 예약 및 hover reveal과 다르다. 도구 등장으로 문서 높이를 바꾸지 않는 원칙은 유지한다. 계약 문서는 바꾸지 않았다. 승인 후 master 기준 새 브랜치에서 기존 도구/키보드 경로를 보존하며 구현해야 한다.

## 실행 방법

1. 이 스파이크 브랜치를 checkout하고 의존성이 준비된 환경에서 `prototype/sample.md`를 `tmp/table-spacing-1481/cursor-sample.md`로 복사한다.
2. 기존 `apps/editor/test/quiet-document.browser.js`를 별도로 백업하고 `prototype/capture.browser.js`로 임시 교체한다.
3. `pnpm browser:test quiet-document --screenshots`를 한 번 실행한다. runner는 검사용 재사용 프로필과 격리된 임시 Host 환경을 사용한다.
4. 원래 시나리오를 복구한다. 결과는 `tmp/table-cursor-prototype/` 및 runner의 scenario-result.json이다. 제품 시나리오를 교체한 상태로 커밋하지 않는다.

로컬 촬영 순회 1/1 통과. 원본 검사 본문 복구, 제품 tracked diff 없음, 시작한 검사 서버·브라우저 종료 확인. 캡처 성공을 제품 수락 성공으로 부르지 않는다.
