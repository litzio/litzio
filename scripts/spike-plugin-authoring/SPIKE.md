# 플러그인 제작 질문 순서 비교

## 질문과 판정

막연한 업무 요청을 받았을 때 질문·계획 후 제작과 화면 시안 후 제작 중 어느 쪽이 더 적은 사용자 응답으로 실제 목표에 도달하는가? 화면의 위치를 말로 알려 주는 수고가 관찰되는가?

과제 요청문, 비서에게 주지 않는 속마음과 7개 판정 항목, 합성 자료는 [tasks.mjs](tasks.mjs)에 있다. 과제 3은 과제 2의 조건을 모두 미리 준다. 과제 1의 보고는 한 폴더에서 매주 버튼으로 모아 새 문서로 쓰고 싶다는 설정이며 여러 주의 처리 방식은 정해 두지 않았다. 과제 2·3에서는 기준값 20에서 표본 가의 26·31, 표본 나의 23만 초과한다. 이어 기준값 30을 입력해 표시가 바뀌는지 확인한다.

사용자 역할은 두 방식에서 같은 규칙을 적용한다.

- 최초 요청과 카드 응답 한 묶음 및 일반 메시지 한 건을 각각 사용자 1턴으로 세고 최대 8턴에서 멈춘다.
- 질문받은 범위에서 속마음만 쉬운 말로 답한다. 정해 두지 않은 항목에는 “잘 모르겠어, 알아서 해 줘”라고 한다.
- 화면을 실제로 띄워 본 뒤 눈에 띄는 차이를 한 번에 최대 두 가지 말한다. 화면이 맞으면 “좋아”라고 한다. 이 수락은 사용자 턴에 포함하되 작업을 끝낸 비서에게는 재전송하지 않아 새 AI 턴을 만들지 않는다.
- 화면의 대상이나 위치를 가리키는 구절을 사용자 발화에 표시한다. 질문 카드의 질문 수와 일반 메시지에서 답을 요구한 질문 수도 합산한다.
- 체크 항목은 실제 브라우저에서 조작하고 화면 및 결과 문서로 확인했을 때만 충족으로 센다.

## 재현

1. master의 제작 지침으로 `pnpm --filter @litzio/cli build`를 실행해 `packages/cli/dist`를 `tmp/plugin-authoring-builds/A`에 복사한다. 이 브랜치의 지침으로 다시 빌드하고 B에 복사한다. 도구·SDK·화면 부품과 Host 실행 로직은 같다.
2. `pnpm exec tsx scripts/spike-plugin-authoring/run.mjs A-1-1`처럼 방식, 과제, 반복으로 식별한 새 실행을 시작한다. Codex `gpt-6.1-terra` high·전체 접근을 사용한다. 매 실행에 새 폴더, Host, 자료, 대화를 쓰고 기존 Codex 로그인으로 연결한다. `pilot-1 --preflight`는 모델 목록과 Host 종료만 확인한다.
3. `tmp/plugin-authoring-runs/<실행>/state.json`으로 대화 상태와 설치를 확인한다. 다음 사용자 턴에 `action-2.json`부터 `{"message":"…","where":[]}` 또는 카드의 `{"answers":{"0":"…"},"where":[]}`를 쓴다. 종료는 `{"stop":true}`를 쓴다. 실행마다 다른 폴더를 사용한다. 원본 대화와 로그는 공개하지 않는다.
4. 해당 실행의 Host URL을 `LITZIO_BROWSER_URL`에, 화면 관찰 설정 JSON 경로를 `LITZIO_SPIKE_AUTHORING_CAPTURE`에 넣고 `pnpm browser:test spike-plugin-authoring`을 실행한다. JSON은 자료 `folder`, 플러그인 표시 `name`, PNG 접두어인 `output`, 화면에서 수행할 `steps` 배열을 사용한다. 브라우저 시나리오는 기존 Windows persistent profile과 실행별 storage 초기화를 재사용한다. 사용자 경로가 표시된 텍스트는 캡처에서 가린다.
5. 실행마다 첫 설치 시점과 마지막 화면의 소스 사본을 따로 보관하고, 최종 채점 시 가짜 데이터가 연결되는지 확인한다. 공개 증거의 경로와 계정 정보를 검사한다.

## 현재 결정과 차이

기존의 빠진 조건 질문과 비자명한 과제의 계획 문서를 먼저 쓰는 절차를, 시안 제작·설치·확인 뒤 기능 연결로 바꿨다. 조건이 충분하면 한 번에 만드는 예외는 두 방식 모두에 있다. 변경한 지침 전문은 [authoring-skill.ts](../../apps/editor/server/plugins/authoring-skill.ts) 첫 부분의 두 문단이다.

## 결과

| 과제 | (가) 첫 화면 → 최종 충족 | (나) 첫 화면 → 최종 충족 | (가) 추가 왕복 | (나) 추가 왕복 |
| --- | --- | --- | --- | --- |
| 주간 보고 | 2·4 → 7·7 | 0·0 → 7·7 | 2·2 | 3·3 |
| 막연한 CSV | 1·1 → 7·7 | 1·0 → 7·7 | 3·3 | 3·2 |
| 조건을 다 준 CSV | 7·7 → 7·7 | 7·7 → 7·7 | 0·0 | 0·0 |

12개 대화 모두 최종 7항목을 브라우저에서 검증했다. 이 중 가짜 자료를 먼저 보여 준 실행은 (나)의 주간 보고 2회와 막연한 CSV 1회다. 이 세 화면의 첫 코드에서 최종본에 같은 줄로 남지 않은 비율은 공백을 제외하면 75%, 75%, 87%였고 가짜 자료는 최종 화면과 처리에서 사라졌다. (나)의 나머지 막연한 CSV는 실제 CSV를 먼저 읽었으며 화면 코드 변경 비율은 50%였다. 조건을 모두 준 CSV는 각 방식 2회 모두 질문 없이 첫 화면에서 7항목을 충족했다.

요청·카드 답변·수락과 화면의 위치를 가리킨 구절은 [user-turns.md](user-turns.md)에 있다. (가)에서는 8개 발화의 15개 구절, (나)에서는 9개 발화의 13개 구절이 화면 대상을 가리켰다. 명시적으로 지목한 곳을 다른 곳으로 잘못 이해한 사례는 관찰되지 않았다. 캡처 40장은 [captures](captures)에 있다.

## 한계와 추천

과제·방식마다 2회씩이며 사용자 역할도 조건을 미리 아는 모델이 맡았다. 브라우저 조작은 측정자가 수행했다. 발화와 읽기 부담은 실제 사람에게 측정하지 않았다. 동시에 진행한 Host와 순서대로 수행한 브라우저 확인 시간이 전체 시간에 들어간다. 제작 대화가 끝난 것과 브라우저가 화면을 확인한 것은 별개다.

시안 우선 지침은 기본값 채택을 보류할 것을 추천한다. 주간 보고의 첫 화면은 빨랐으나 추가 왕복은 두 번 모두 늘었다. CSV에서는 실제 시안을 사용한 한 대화에서 한 번 줄었다. 요소 선택 기능은 비교 대상에 없었고 위치 오인도 관찰되지 않아 개발 우선순위를 정할 근거는 부족하다.
