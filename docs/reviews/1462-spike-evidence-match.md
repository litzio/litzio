## 판정

**종합 실패다.** 주입 오류의 탐지 기준은 네 종류 모두 통과했지만, 정상 입력 경보는 간단한 규칙 적용 뒤에도 페이지당 1건을 크게 넘었다. 이 방식은 텍스트 누락·변조의 독립 증거를 제공할 수 있으나, 현재 형태로 검수자에게 결정적인 저잡음 경보를 제공한다고 판단할 수 없다.

| 사전 기준 | 규칙 적용 전 | 규칙 적용 후 | 판정 |
| --- | --- | --- | --- |
| 문단 삭제 3건 중 2건 이상 | 3/3 | 3/3 | 통과 |
| 숫자 변조 3건 중 2건 이상 | 3/3 | 3/3 | 통과 |
| 문단 순서 변경 3건 중 2건 이상 | 3/3 | 3/3 | 통과 |
| 표 칸 삭제 3건 중 2건 이상 | 3/3 | 3/3 | 통과 |
| LSR 정상 13쪽, 평균 경보 ≤1/쪽 | 71건 / 13쪽 = 5.46 | 60건 / 13쪽 = 4.62 | 실패 |
| NIST 정상 3쪽, 평균 경보 ≤1/쪽 | 18건 / 3쪽 = 6.00 | 15건 / 3쪽 = 5.00 | 실패 |
| 두 입력 합계, 참고값 | 89건 / 16쪽 = 5.56 | 75건 / 16쪽 = 4.69 | 실패 |

요청된 채점 정의에 따라 **주입 전 최초 변환 문서에서 나온 경보는 전부 오경보로 계산**했다. 최초 변환에는 실제 구조 손실·수식 오인식도 있으므로, 아래 수는 독립적인 정답 판정으로 확정한 false-positive precision이 아니라 정상 입력에서 사람이 검토해야 하는 보수적 경보 예산이다. 실제 손실을 분모에서 빼서 합격시키지 않았다. NIST는 보조 정상 입력이며 오류 주입은 LSR에서만 했다.

## 입력과 보존

LSR는 [보관된 CC0 합성 PDF](../../community-plugins/docling/sample/lsr-1.1/README.md) 13쪽 전체다. 이 worktree에는 이전 JSON이 없어서 기존 `docling-serve` 컨테이너를 시작하고 기존 `convertPdfToArchive`와 변경하지 않은 `litzio-pdf-en-v1` 프로필로 한 번 변환했다. 서버 1.32.0 / Docling 2.124.0 / core 2.93.0이었다. **JSON 해시가 P1a·P1b 및 앞선 렌즈 측정과 같은 `fc3a…098d`로 재현됐다.** 프로필의 OCR·수식 enrichment는 기존 변환 처리다. 별도 AI 검수·생성 호출은 0회다.

보조 입력은 [보관 이력](https://github.com/litzio/litzio/tree/ce90560aacaee2482d37c4b25e36e93060ed156c/plugins/docling/test/fixtures/nist-sp1108r4)의 NIST SP 1108r4 PDF와 기존 JSON을 그대로 사용했다. PDF 발췌본의 물리 6·9·10쪽(인쇄 17·20·21쪽)만 측정했다. 새 발췌 PDF나 새 변환은 만들지 않았다. 전체 원본 JSON을 현행 변환기에 전달한 후, 변환 report의 target과 원래 provenance로 해당 3쪽의 리치오 출력 단위를 선택했다. PDF 증거는 선택된 페이지의 모든 텍스트를 유지했다. 이 선택은 표본 범위 지정이며 Docling이 찾지 못한 PDF 항목을 버리는 필터가 아니다.

| 입력 | PDF SHA-256 | 변경하지 않은 DoclingDocument SHA-256 |
| --- | --- | --- |
| LSR 13쪽 | `63cda884de96dfd0357843a534895f1beb7a10b24f3244398d930817a32b82ea` | `fc3a4b657e3bbd530c245226f191a8b9b9b53b3e1ab5f599389323aa7c47098d` |
| NIST 발췌본 중 3쪽 | `5be90726ae6ff9cf0383fbb5ad76167c0f51328545782c37411fb27892143820` | `9940863e6110fea3ca065e65d3dc9da573b7f807a7b2a8edcf32688a67f3927d` |

리치오 최초 문서는 현행 `community-plugins/docling/document.js`의 `convertDocument` 결과를 그대로 사용했다. Core `parse`·`getEditableDocument`에서 읽고, 주입은 기존 Core 의미 연산으로 독립 적용했다. 최초 문서와 변형의 canonical write, 변형 serialize→parse→serialize 일치, 원본 JSON 불변을 확인했다. 최초 리치오 source 해시는 작은 fixture에 있다. 제품 코드·SDK·저장 형식·화면·설계 계약은 변경하지 않았다. 큰 PDF/JSON/이미지와 전체 실행 결과는 ignored `tmp/evidence-match/`에만 둔다. 문서 색인 제외는 병합하지 않는 spike에 대한 요청을 따른다.

## 알고리즘과 경보 단위

PDF.js `getTextContent`의 문자열과 viewport 좌표를 페이지별로 추출했다. baseline 높이가 2pt 이내인 항목을 한 줄로 묶고 y→x 순서로 읽었다. 다단·표·수식 구조는 추정하지 않는다. 리치오 쪽은 Core의 문단·제목·표 칸·목록 항목·캡션·수식/코드 읽기 모델을 문서 순서로 펼친다. native 표·그림 번호와 순서 목록 번호도 포함한다. 공백, 글자 NFKC/합자, soft hyphen, 글자-줄끝 하이픈-다음 소문자만 정규화하고 대소문자·숫자·단위·비교 기호·위/아래첨자 숫자는 유지한다. 두 토큰열의 전체 LCS를 계산해 PDF 쪽 비대응은 누락 후보, 리치오 쪽 비대응은 근거 없는 추출·중복 후보로 남긴다. LSR 대응에는 Docling provenance를 전혀 쓰지 않는다. 문서에 흔적이 없는 PDF 텍스트도 비교에 남는다.

LCS의 연속된 비대응 구간 하나가 경보 하나다. 인접 삭제·삽입은 한 교체 경보로 세고, 페이지를 넘는 구간은 PDF 페이지별로 나눈다. 경보 사이에 대응 토큰이 있으면 합치지 않는다. 따라서 긴 그림 내부 문자열 100개가 하나의 경보에 들어갈 수 있고, 수식 하나가 여러 경보로 나올 수 있다. 토큰 수·원문 위치·블록 위치·전체 gap과 matches를 원시 결과에 보존했다. 이 경보 개수를 의미 오류 개수로 해석하지 않는다. 단일 경보에 원문 토큰이 없을 때 페이지는 가장 가까운 PDF anchor로 표시하므로 검토 화면용 정확한 귀속을 보장하지 않는다.

간단한 후처리 규칙은 PDF만 보며, 페이지 위·아래 8%에서 발견된 순수 아라비아 쪽 번호 또는 **정확히 같은 글자가 선택된 3쪽 이상에서 반복되는 줄**을 제외한다. 숫자를 wildcard로 바꾸지 않았다. LSR 39줄·208토큰, NIST 3줄·3토큰이 제외됐다. Docling의 furniture label이나 표·그림·수식 종류로 경보를 숨기지 않았다. 첫 측정 뒤 규칙·대상·임계값을 바꾸지 않았다. 결과를 본 후 baseline에서 빠진 문구에 맞춰 규칙을 늘리지 않았다.

전체 LCS는 O(P×L) 시간·공간이다. 이번 최대 행렬은 9,530,564 bytes였다. 1.4억 Uint16 cell 한도를 넘는 입력은 실패하도록 했다. 범용 인덱스·복잡한 정렬 엔진·새 저장 형식은 만들지 않았다.

## 오류 주입과 탐지 근거

최초 비교 전에 문서 순서의 20%·50%·80% 인덱스 `floor((n-1)×q)`를 고정했다. 문단 후보는 80자 이상, 숫자는 그중 ASCII 숫자를 가진 문단, 칸은 4자 이상의 비어 있지 않은 칸이다. 탐지되는 대상을 찾는 재선택은 하지 않았다. 각 변형은 최초 문서에서 시작하며, 12개 오류를 누적하지 않았다.

삭제는 기준 문서에서 대응했던 target 증거가 **새로** 비대응이 되었으며 target 전체 토큰과 기존 대응 토큰 양쪽의 절반 이상을 덮을 때 탐지로 셌다. 숫자는 원래 숫자의 신규 PDF 비대응과 바뀐 숫자의 신규 리치오 비대응을 함께 요구했다. 순서 변경은 영향 구간에 새로 비대응이 된 연속 8토큰 이상이 반대쪽에도 같은 순서로 존재할 때 셌다. 기존 경보의 존재나 경보 총수 증가만으로 성공 처리하지 않았다.

| 종류 | 사전 선택 위치(Core path) | 실제 변경 | 적용 전/후 탐지 |
| --- | --- | --- | --- |
| 문단 삭제 | `[13]`, `[38]`, `[78]` | 설명 NOTE, 표 수식 설명, Figure K.2 설명을 각각 삭제. 대응 토큰 31·24·28개 | 각각 3/3 |
| 숫자 변조 | `[16]`, `[39]`, `[65]` | 첫 숫자 17→27, 19→29, Figure K.1→K.2 | 각각 3/3 |
| 문단 순서 | `[13]`, `[38]`, `[76]` | 선택 문단을 다음 80자 이상 문단 뒤로 이동 | 각각 3/3 |
| 표 칸 삭제 | `[23,5,1]`, `[34,1,1]`, `[48,1,0]` | `Noel Ash`, `Profile A`, `r > 6.4 Hz`를 각각 빈 칸으로 교체 | 각각 3/3 |

모든 주입 target은 최초 LCS에서 전체 토큰이 대응했고, 원시 match의 PDF page/line을 확인해 실제 해당 원문에 붙었는지 확인했다. `Profile A` 삭제는 반복되는 `Profile`이 다른 칸과 계속 대응해 신규 누락 1/2토큰으로 탐지됐다. 순서 2번은 이동한 문단을 그대로 대응시키고 사이 문단을 양방향 비대응으로 남겼다. 순서 3번은 총 경보 수가 baseline과 같아도 새 위치 불일치로 탐지됐다. 이 사례들은 단순 경보 개수 증가를 탐지로 삼으면 안 되는 이유다.

숫자 후보가 우연히 각주 표식·그림 참조에 모였다. 실제 측정값·단위·부등호 변조의 문서별 recall을 측정한 것은 아니다. 엄격 비교 자체는 별도 작은 sanity check에서 `12.5→12.6`, `µA→mA`, `≤→<`, `²→2`를 양방향 차이로 확인했다. 단순 삭제·중복도 확인했다. 이것을 실제 문서의 추가 주입 사례나 제품 테스트 통과로 합산하지 않는다.

## 오경보 원인

주입 전 경보 89건과 규칙 후 75건을 전부 읽고, 대표 PDF 페이지를 렌더링해 구조·회전 문구·그림을 확인했다. 원인 label은 사람이 붙였으며 알고리즘에는 사용하지 않는다. 복합 gap은 주원인 하나로 분류했다. 예를 들어 LSR의 캡션+각주 혼합 gap은 표·캡션에 넣었다. 표의 합계는 중복 집계가 아니다.

| 주원인 | LSR 전→후 | NIST 전→후 | 합계 전→후 | 간단한 완화 가능성과 누락 은폐 위험 |
| --- | --- | --- | --- | --- |
| 머리말·꼬리말·쪽 번호 | 27→16 | 6→3 | 33→19 | 적용 규칙으로 일부 감소. LSR는 꼬리말과 쪽 번호가 같은 줄에 합쳐지고 NIST는 왼쪽 회전 출판 문구라 남는다. 띠 확장·숫자 제거 반복 판정은 진짜 본문·숫자 차이를 숨길 위험. |
| 표·캡션 순서·병합 칸 반복 | 18→18 | 0→0 | 18→18 | 캡션을 표 앞뒤로 허용하거나 병합 칸 반복을 인지하면 줄일 여지. 단순 중복 제거는 실제 중복과 잘못된 칸 배치를 숨긴다. |
| 그림 안 글자·그림 읽기 순서 | 8→8 | 1→1 | 9→9 | LSR K.1/NIST 그림은 raster 내부 OCR 글자에 PDF 텍스트 증거가 없고, K.2는 축·캡션 순서가 다르다. 그림 전체 제외는 실제 label 누락·변조를 가리므로 적용하지 않음. |
| 수식 표현·오인식 | 6→6 | 0→0 | 6→6 | PDF glyph와 LaTeX를 그대로 비교하면 부합하지 않는다. 수식 전체 제외는 숫자·근호 차수·상한의 실제 오류도 가린다. 수식 렌즈 재구현은 범위 밖. |
| 각주·위첨자 읽기 순서 | 9→9 | 2→2 | 11→11 | 작은 표식의 y 위치와 본문/각주 순서 차이. 표식을 숫자 본문에 흡수하거나 무시하면 실제 참조·값 오류를 숨긴다. |
| 다단 읽기 순서 | 3→3 | 0→0 | 3→3 | LSR 11쪽의 나란한 Route A/B 표가 PDF에서는 줄 단위로 섞인다. 열별 정렬은 완화 가능하지만 표 안 정당한 행 순서·순서 오류를 바꿀 수 있다. |
| 문장부호 원형 | 0→0 | 9→9 | 9→9 | dash/apostrophe를 같은 문자로 보면 감소 가능. 빼기·범위 부호까지 합치면 의미 차이를 가릴 수 있어 이번에는 유지. |
| 하이픈·줄바꿈 | 0→0 | 0→0 | 0→0 | 정규화 후 별도 잔여 gap 0건. 원래 하이픈이 의미 있는 합성어라면 잘못 합칠 위험이 있어 문자-줄끝-소문자로 한정했지만 완전한 판별은 아니다. |
| **전체** | **71→60** | **18→15** | **89→75** | **간단한 규칙만으로 1건/쪽에 도달하지 못함.** |

위험 검토는 해당 규칙의 안전성을 실제 모든 문서에서 증명한 것이 아니다. LCS에서 흔한 숫자·단어가 다른 위치와 대응할 수 있고, 긴 블록의 작은 변화가 gap을 갈라 경보 수가 비단조적으로 달라질 수 있다. 한 gap은 한 의미 문제와 일치하지 않는다. 분류를 바꿔도 총 경보 수는 줄지 않는다.

| 실험 본체 전체 | 5.438초, module import·CLI 시작 제외. 변형 생성·Core 검증·원시 결과 쓰기 포함 |

최초 본체 실행은 4.263초였고, sanity/round-trip 검증을 보완한 재실행은 위 5.438초다. 마지막 확인 실행은 4.530초였으며, 보관한 측정 fixture와 source·경보 fingerprint 및 24개 판정의 일치를 summarizer로 검증했다. 측정 fixture는 5.438초 실행 수치를 보관한다. 성능 반복 분포·cold I/O·큰 문서의 상한은 측정하지 않았다. 초기 `pnpm install --frozen-lockfile`은 lockfile을 바꾸지 않았다.

검증은 실제 PDF/변환 JSON에 대한 오프라인 스크립트 실행, Core 공식 쓰기·round-trip 단언, 전체 baseline label 누락/중복 검사, 입력/source/경보 fingerprint 재현, 코드 문법과 diff 검사를 사용했다. 제품 런타임·Host 저장·브라우저·SDK worker·AI 사용자 흐름·CI를 검증한 결과가 아니다. 새 PR은 만들지 않는다.

`pnpm docs:check`는 이 보고서가 docs index에 직접 연결되지 않았다는 1건으로 실패했다. 요청에 명시된 비병합 spike의 색인 제외를 유지했고 checker나 색인을 바꾸지 않았다. 이 예외를 문서 검사 전체 통과로 보고하지 않는다.

## 제품화한다면 필요한 최소 범위와 위험

지금 결과로 자동 교정이나 검수 완료의 근거로 채택하지 않는다. 다음 최소 검증은 텍스트가 실제로 있는 본문 영역에 한정한 독립 후보와 PDF page/bbox·리치오 block locator를 함께 보여주고, 사람이 확인할 수 있는지 측정하는 것이다. 문단·표·수식·이미지별 **증거 없음과 내용 불일치를 구별하는 범위 표시**, 국소적인 읽기 순서 차이의 취급, 새 문서에서의 오경보 예산 검증이 먼저 필요하다. 이 실험에서는 구현하지 않았다.

텍스트 레이어가 있는 PDF도 수식·그림 일부는 이미지/outline일 수 있다. LSR 5·11쪽의 표 수식처럼 PDF 텍스트 증거에도 내용이 없으면 Docling과 PDF.js 양쪽이 놓친 내용을 이 방법은 발견할 수 없다. NIST 그림 내부 OCR 글자에 근거가 없다는 경보도 곧바로 잘못된 추출이라는 결론이 아니다. PDF 글자 코드 자체가 틀린 경우 역시 시각 원본의 정답을 보장하지 못한다.

텍스트 레이어 없는 스캔 PDF, 새 OCR, 이미지 의미·graph 연결, 정확한 수식 동치, 각주/캡션 연결 의미, 표 span·행열 의미, 문서 형식 일반화, 100/300쪽 확장과 UI 수락은 범위 밖이다. 단순 규칙 다음에는 구조 대응이 필요해 보이나, 여기서는 더 복잡한 정렬 엔진으로 확장하지 않고 실패와 원인을 남긴다.

기존에 중지되어 있던 `docling-serve`만 이 실행에서 시작했다. 종료 때 그 컨테이너를 다시 중지해 `exited`를 확인했고, 준비/실험 프로세스는 exit 0으로 종료됐다. 사용자가 실행 중이던 서버나 다른 작업의 프로세스는 정리 대상에 넣지 않았다.
