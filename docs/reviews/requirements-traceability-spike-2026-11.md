# 요구사항 추적 spike: 표준 문서 → 시스템 요구사항 문서, ReqIF 내보내기

- Status: Historical
- Measured: 2026-11-11, Linux x64, Node 24, StrictDoc 0.30.4, lxml(libxml2) 스키마 검증.
- Branch/base: `spike/requirements-traceability` / `31bfd8d6` (`origin/master`). 로컬 커밋만 있으며 push·PR 없음.
- Scope: 제품 계약이 아니라 실험 기록이다. 채택 여부와 후속 범위는 소유자 결정이다. 사용한 표준 문서 본문과 캡처는 저작권 때문에 저장소에 넣지 않았다. 아래 수치는 저장소 밖의 로컬 실행 결과다.

## 무엇을 시험했나

표준 요구사항 문서(왼쪽)와 시스템 요구사항 문서(오른쪽)를 **둘 다 평범한 Litzio 문서**(`litzio: 1`)로 두고, 각각 따로 저장·열기·편집하면서 문장 단위 추적이 성립하는지 확인했다.

- 왼쪽: IEEE Std 1547-2018 4–6장을 Docling 변환본에서 Litzio 문서로 옮긴 표준 문서. 규범 문장(shall/should/may) 265개(shall 219 · may 45 · should 1; 4장 78 · 5장 45 · 6장 142).
- 오른쪽: 제목·목적·범위·용어·장/절 구조와 요구사항 블록을 가진 자기완결적 시스템 요구사항 문서. 문장은 시스템 관점으로 다시 쓴다(DER → "DER 시스템"). 표준 문서로 가는 연결은 **요구사항 블록의 `:source:` 속성뿐**이다.
- 추적은 한 단계(표준 문장 → 시스템 요구사항)만 모델링한다. 상·하위(`:parent:`) 구조는 속성과 ReqIF 관계로 열어 두었을 뿐 의미 규칙은 없다.
- 최종 산출물은 ReqIF 1.2 파일이다.

## 모델

### 요구사항 블록

MyST 지시문 하나이며 정식(canonical) 형태만 허용한다. 옵션 순서와 본문 형식이 고정이라 열고 저장해도 바이트가 같다.

````markdown
```{requirement} 제어 모드 전환 개시 시간
:id: REQ-1547-0107
:status: reviewed
:type: performance
:strength: shall
:source: ieee-1547-2018.md#std-4-6-3-p1~s1@<12자리 해시>
:parent: REQ-1547-0100

DER 시스템은 로컬 통신 인터페이스가 모드 설정 변경을 수신한 뒤 30초 이내에 모드 전환을 시작해야 한다.
```
````

| 속성 | 값·규칙 |
| --- | --- |
| `id` | 영구 식별자. `[A-Za-z][A-Za-z0-9._-]{0,63}`. 문서 안에서 유일해야 하며 연산은 중복 삽입과 변경을 거부한다. 중복 ID는 열기는 되지만 점검이 오류로 보고한다. |
| 제목 | 지시문 인수. 한 줄. |
| `status` | draft · reviewed · approved · obsolete |
| `type` | functional · performance · interface · safety · constraint · information |
| `strength` | shall · should · may |
| `source` | `<문서>#<앵커>~s<문장번호>@<해시>` 공백으로 여러 개. |
| `parent` | 같은 문서의 다른 요구사항 ID(선택, 존재 여부만 점검). |
| 본문 | 일반 텍스트. 코드 펜스·`:::` 시작 줄은 거부. |

Core는 `insertRequirement`·`updateRequirement`(ID 변경 거부)·`assignAnchors`와 편집 모델의 `requirement` 블록을 추가한다. 네이티브 수용 목록은 이 정식 형태만 새로 받아들이며, 잘못된 블록은 이유와 함께 거부한다.

### 앵커와 변경 감지

- 표준 문서의 규범 단락 앞에 MyST 대상 `(std-<절>-p<번호>)=`를 둔다(`assignAnchors`; 이미 있으면 유지, 반복 실행해도 같음).
- 문장은 `앵커~s<번호>`로 지정하고, 정규화한 문장(NFC·공백 정리)의 SHA-256 앞 12자리를 함께 저장한다.
- 같은 번호의 문장이 해시와 다르면 `source-changed`(오류). 해시가 같은 문장이 같은 단락의 다른 위치에 있으면 `source-moved`(경고)로 찾아 준다. 앵커가 없으면 `broken-link`.
- 규범 문장은 소문자 shall/should/may만 센다("May"는 달 이름). "Note a:" 같은 설명 문장은 제외한다.

## 흐름

1. **추출**: `extract`가 아직 요구사항도 제외도 아닌 규범 문장을 후보로 낸다(조항·강도·추정 유형 포함).
2. **검토**: 후보마다 **채택**(`adopt`: 같은 조항 절 끝에 draft 블록 삽입, 문장은 규칙 기반으로 시스템 관점 재작성) 또는 **제외**(`exclude`: 문서 옆 `<시스템문서>.excluded.json`에 앵커·문장번호·해시 기록. 해시가 바뀌면 제외가 풀린다). 되돌리기 지원.
3. **초안**: `draft`는 모든 후보로 시스템 문서를 새로 만든다(덮어쓰지 않음). 이번 문서는 이 초안에 한국어 도입부(목적·범위·용어)를 붙이고 문장 17개를 손으로 다듬어(status reviewed) 만들었다. 나머지는 영어 원문을 규칙으로 재작성한 draft다.
4. **점검**: `check`가 고아·깨진 링크·원문 변경·이동·중복 ID·존재하지 않는 상위·강도 불일치·미추출 문장을 낸다.
5. **내보내기**: `export`가 ReqIF 1.2를 만든다.

## 사용 방법

- **CLI**(ADR-0015): `litzio requirements check|extract|adopt|exclude|anchor|draft|export --standard <표준> --system <시스템> [--key <앵커~sN>]… [--out <파일>] [--strict] [--json]`. `check`는 오류가 있으면 종료 코드 1이며 `--strict`는 미추출도 실패로 본다.
- **HTTP**: `POST /api/requirements` — CLI와 같은 `executeRequirementsOperation`(`apps/editor/server/requirements.ts`). 읽기는 순수하고, 쓰기는 Core 연산과 revision 확인 쓰기를 쓴다.
- **편집기**: 요구사항 블록은 카드(ID·제목·상태·유형·강도 배지, 본문, 출처 링크)로 보인다. **편집**을 누르면 속성 패널(제목·상태·유형·강도·본문·출처 링크·상위 ID)이 열리고 ID는 읽기 전용이다. 저장은 기존 diff 경로(Tiptap → `requirements` 편집 → Core `updateRequirement`)를 따른다.
- **비교 탭**(명령 센터 → "요구사항 비교"): 왼쪽 표준, 오른쪽 시스템을 둘 다 읽기 전용 문서로 렌더한다. 한쪽 블록을 선택하면 반대쪽 대응 블록이 강조되고 연결선이 그려진다(선택한 연결은 굵게). 스크롤은 대응 위치 기준으로 동기화한다(해제 가능). 추출되지 않은 규범 단락에는 **미추출** 표시가 붙고, 상태 줄은 `요구사항 N · 연결 N · 미추출 N`을 보인다(연결 = 해소된 출처 링크 수). 아래 패널은 후보 검토(채택/제외/되돌리기), 추적 점검, 조항별 추적 매트릭스를 담는다. **ReqIF 내보내기** 버튼은 같은 연산의 결과를 파일로 내려받는다.

## ReqIF 1.2

| 요소 | 내용 |
| --- | --- |
| 스키마 | 기계가 읽는 스키마는 1.0.1부터 같다. 네임스페이스 `http://www.omg.org/spec/ReqIF/20110401/reqif.xsd`, `REQ-IF-VERSION`은 XSD가 `1.0`으로 고정한다. |
| SPEC-OBJECT-TYPE | Section(제목), Information(일반 본문·표), Requirement(ID·제목·본문 XHTML·status·type·strength·source·parent), SourceSpan(표준 문장 지정자) |
| 속성 이름 | StrictDoc 등이 알아보는 관례 이름(`ReqIF.ForeignID`, `ReqIF.Name`, `ReqIF.ChapterName`, `ReqIF.Text`)을 쓴다. 본문은 XHTML. |
| 관계 | `RT-TraceToStandard`(요구사항 → 표준 문장 지정자), `RT-Parent`(상위 요구사항) |
| SPECIFICATION | S-1은 시스템 문서의 절 계층을 따른다. S-2는 참조된 표준 문장 지정자 목록(관계 대상이 ForeignID를 가져야 StrictDoc가 읽는다). |
| 표준 본문 | 내보내지 않는다. 앵커·문장번호·해시만 나간다. |

### 검증

- **공식 XSD**: OMG의 `reqif.xsd`·`driver.xsd`와 의존 스키마를 로컬로 받아 `schemaLocation`만 로컬 경로로 바꿔 `lxml`로 검증했다. 시스템 문서 전체 내보내기(252 요구사항, 편집기에서 내려받은 파일 포함)와 시험용 문서가 모두 유효하다. 일부러 깨뜨린 파일은 거부됨을 확인했다. 검증 스크립트는 `scripts/validate-reqif.py`이며 core 테스트는 스키마·`python3`+`lxml`이 있을 때만 이를 호출하고, 없으면 건너뛴다고 진단 메시지를 남긴다.
- **StrictDoc 0.30.4**: `strictdoc convert --input-format reqif-sdoc --output-format sdoc --reqif-import-markup HTML` 로 가져와 252개 요구사항(UID·제목·상태·유형·강도·출처)과 252개 `Parent` 관계(`TraceToStandard`)가 복원됨을 확인했다. 첫 시도는 관계 대상 유형에 ID 속성이 없어 실패했고, SourceSpan에 `ReqIF.ForeignID`를 넣고 별도 SPECIFICATION으로 두어 해결했다. StrictDoc에는 `import` 하위 명령이 없고 `convert`가 그 역할이다. 지원 프로필은 P01_SDOC뿐이다.

## 한계와 열린 문제

- 정규화한 문장 해시가 같으면 같은 문장으로 본다. 의미는 바뀌지 않았지만 표현이 바뀐 경우를 거르지 못하고 "원문 변경"으로 보고한다. 반대로 같은 문장이 두 번 나오면 첫 일치를 쓴다.
- 앵커는 최상위 단락만 지원한다. 표 안의 문장과 목록 항목은 스캔하지 않는다(이번 표준 문서는 목록 항목을 단락으로 풀어 옮겼다). 표준 문서가 자주 바뀌면 단락 번호(`p<n>`) 기반 앵커가 흔들릴 수 있어 사람 이름 붙이기나 내용 기반 앵커가 필요할 수 있다.
- 문장 재작성은 규칙 기반이라 제목이 어색하거나 조각 문장이 남는다(`제외`로 처리). 자연스러운 한국어 문장은 사람이 다듬었고(17개), 대량 번역·재작성은 범위 밖이다.
- 요구사항 본문은 일반 텍스트다. 표·수식·그림·인라인 서식은 없다.
- 요구사항 블록 삽입은 비교 탭의 채택으로만 만든다. 일반 편집기의 새 블록·복사·붙여넣기·이동(순서 변경)은 다루지 않았다(복사는 ID 중복을 막으려고 막혀 있다).
- 비교 탭은 두 문서를 읽기 전용으로 렌더하고, 채택/제외는 파일에 바로 쓴다. 같은 시스템 문서가 다른 탭에서 편집 중이면 기존 외부 변경 흐름에 맡긴다. 문장 단위 강조는 블록 단위 강조와 하단 상세 줄로 대신했다(단락 안 문장 범위 강조 없음).
- 시스템 문서에 해당 조항의 절이 없으면 채택한 블록은 가장 가까운 상위 절 끝이나 문서 끝에 붙는다. 절 제목은 자동으로 만들지 않는다.
- ReqIF: 한 요구사항이 표준 여러 문장을 가리키는 경우는 관계 여러 개로 나가지만, 역방향·다대다 품질은 시험하지 않았다. 도구별 가져오기는 StrictDoc만 확인했고(한국어 본문 OK), DOORS·Polarion 등은 시험하지 않았다.
- 상·하위 구조(`:parent:`)와 개정 이력·승인 흐름은 열어 두기만 했다.
- 비교 탭의 경로 입력은 문서 경로를 직접 적는 단순한 형태이며 마지막 쌍을 브라우저에 기억한다.
