# 테스트 설계와 PR 확인

- Status: Implemented
- Last verified: 2026-11-03 — #1009 합의안·소유자 결정과 기존 Verification 규칙을 문서 대조. 제품 테스트 실행은 포함하지 않음.
- Scope: 테스트 작성·확대와 PR 단위 확인에 적용하는 작업 지침.
- Decision: [#1009 합의안](https://github.com/litzio/litzio/issues/1009#issuecomment-6592616212), [소유자 승인](https://github.com/litzio/litzio/issues/1009#issuecomment-6592638567).

실행할 검사의 선택은 [Verification matrix](../../CONTRIBUTING.md#verification-matrix)를 따른다. 기존 테스트 보완을 우선하고, 아래 원칙으로 추가 검사의 고유한 보호 가치와 비용을 판단한다.

## 재발 방지 원칙

1. **각 결함·단언의 주된 검증 계층을 정한다.** 같은 결함을 계층마다 반복하지 않는다. Core 의미, Windows 파일 경계, 실제 브라우저 연결처럼 위험이 다르면 각각 검증할 수 있으며, 서로 다른 보호를 설명한다.
2. **공통 입력 조합은 낮은 계층에 집중한다.** 상위 계층은 연결과 실제 환경 차이를 대표 사례로 검사한다. 전수 조합은 조합 사이의 상호작용이 별도 결함을 만들 수 있다는 근거가 있을 때 사용한다.
3. **무거운 전수 조합은 영향 경로와 릴리스에 집중한다.** 대표 packaged·Save/Reload·실제 프로세스 복구 보호는 일괄 축소하지 않는다. 영향 경로 밖에서도 전체 실행이 필요하면 대표 사례가 놓치는 위험과 실행 조건을 설명한다.
4. **정상 기능 검사에 근거 없는 짧은 속도 기준을 섞지 않는다.** 명시된 응답성 계약과 무한 대기 방지 제한은 유지하며, timeout·취소 fault는 의도적으로 재현한다. 실제 성능 계약을 검증하는 경우 측정 대상과 실행 전제를 명시하고, 실패를 감추려고 제한을 늘리지 않는다.
5. **자동 판정에 쓰이지 않는 성공 캡처와 촬영 전용 순회는 수동 검토로 분리한다.** 픽셀 단언의 입력과 실패 진단 캡처는 허용한다. 시각 변경의 Before/After 검토 근거는 별도 수동 검토 절차에 따라 남긴다.
6. **우연한 변수명·표시 문구보다 공개 동작과 명시적 의존 경계를 검사한다.** 문구나 이름 자체가 공개 계약이면 그 계약을 검사할 수 있다. 새 분석 프레임워크를 기본 해법으로 삼지 않고 기존 검사로 보호할 수 없는 경계가 있는지 먼저 확인한다.
7. **새 경로·스크립트의 실행 소비자와 기존 CI 분류를 확인한다.** 실제 호출 경로와 선택되는 검사를 PR에서 확인한다. allowlist 추가는 의무가 아니며, 근거가 부족하면 unknown full을 유지할 수 있다.

## PR 단위 기록과 확인

테스트나 시나리오·조합을 추가·확대하면 기존 검사와 다른 결함, 주된 검증 계층과 실행 경로를 적는다. 전수 조합·새 subprocess·무거운 E2E를 추가하면 대표 사례로 충분하지 않은 이유와 관측 실행 시간 또는 미측정 사유를 덧붙인다.

검토자는 위 기록과 diff를 대조해 불필요한 보호 중복, 근거 없는 전수 조합, 실행 범위 확대, 자동 판정에 쓰이지 않는 CI 성공 캡처를 확인한다. 시나리오 수·시간 상한을 강제하는 CI나 정기 감사 절차는 추가하지 않는다.
