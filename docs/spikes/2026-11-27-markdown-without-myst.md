# 2026-11-27 MyST 없이 CommonMark·GFM과 리치오 확장으로 문서 의미 담기

- Status: Historical
- Date: 2026-11-27 (브랜치 마지막 커밋일, KST)
- Last verified: 2026-11-27, Windows 11, Node 24.22.3, rustc 1.100.0(GNU 툴체인), markdown-rs 1.0.0, remark-parse 11, mdast-util-to-markdown 2.2.4.

## 목적

MyST를 걷어내고 CommonMark·GFM에 리치오 확장 몇 개를 얹어 remark(micromark/mdast) 계열로 읽고 쓸 수 있는지 확인했다. 질문은 네 가지다.

1. 지금 Core의 문서 의미를 잃지 않는가.
2. 속도가 지금과 어떻게 다른가.
3. markdown-rs(Rust)가 같은 mdast로 읽는가.
4. 조건부로, 제목·문단·인라인 서식·목록·단순 표 범위의 Rust 부분 파이프라인을 실측한다.

2026-11-20 조사("MyST 유지")에서 보지 않은 선택지다. 진행 중에 소유자가 방향을 하나 더 줬다. 확장 문법을 새로 만들지 말고 외부 도구와 호환되는 기존 관례로 "프로필"을 구성하라는 것이다. 그래서 두 프로필을 같은 자료로 쟀다.

## 무엇을 만들었나

**두 프로필**

| 프로필 | 구성 |
| --- | --- |
| directive | remark-directive의 `:::`·`::`·`:name[]`로 리치오 의미를 표기 |
| external | GitHub alerts, Pandoc 속성·fenced div·인용, Quarto `@` 상호참조, 원시 HTML 표 같은 외부 관례를 CommonMark·GFM mdast와 원문 위치에 대한 후처리로 인식. 새 파서 확장은 만들지 않음 |

두 프로필 모두 GFM 자동 링크와 한 물결표 취소선은 끈다. Core가 linkify를 끄고 있어서다.

**같은 의미의 기준**

- Core 공개 읽기 모델(`getEditableDocument`)에서 스냅샷 위치(`path`)와 파생 표시 글자(`text`), `editable`만 뺀 값에 머리말 객체를 더해 비교한다.
- 새 형식으로 쓰고 다시 읽은 결과가 이 값과 같아야 한다.
- 두 번째 쓰기의 바이트도 처음과 같아야 한다.

**자료**

- 네이티브 문서 39개(Core 수용 38): 픽스처, 샘플, 병합 칸 표, 코퍼스에 없던 기능을 모은 합성 문서.
- 바이트 회귀 생성 사례 987건.
- #1983과 같은 혼합의 합성 300·2,300·5,000블록 문서.
- Core 연산 무작위 편집 퍼징 10,000건. Core가 받아들인 9,850건만 셌다.

**Rust**

- markdown-rs mdast 비교 도구.
- 4단계 파이프라인: markdown-rs 읽기 → 리치오 모델 → 정규 Markdown 쓰기. 쓰기는 직접 짰고, mdast-util-to-markdown의 이스케이프 규칙을 이식했다. 네이티브 실행 파일과 WASM 두 가지로 빌드했다.

## 결과·관찰

### 질문 1. 의미 보존

| 프로필 | 네이티브 38 | 생성 987 | 합성 3 | 퍼징 9,850 |
| --- | --- | --- | --- | --- |
| directive | 38 일치 | 987 일치 | 3 일치 | 9,849 일치, 1 거부 |
| external(라벨 접두사 이름 바꾸기 포함) | 33 일치, 5 인용 역할 차이, 쓸 수 없는 블록 4 | 987 일치 | 3 일치 | 4,712 일치 |

directive 프로필은 지금 Core 의미를 잃지 않았다. 다만 지시문 이름·속성은 모두 리치오 규칙이다. 퍼징에서 거부된 1건은 빈 체크 항목이다. GFM은 remark·markdown-rs 모두 `* [x]`만 있는 줄을 체크 항목으로 읽지 않는다. 두 프로필에 공통인 빈틈이다.

external 프로필은 대부분 1:1로 담았다(GFM 표·체크·각주·취소선, `$` 수식, `<sub>`·`<sup>`, Mermaid, YAML 머리말, 알림 5종). 외부 관례에 대응 형식이 없어 새 규칙이 필요한 것은 다음과 같다.

- `{cite}` 기본 역할과 여러 키 서술형 인용(Pandoc은 두 형식뿐).
- Quarto 접두사가 없는 라벨(`@` 참조의 역할을 정할 수 없음).
- 제목 앞이 아닌 구역 대상.
- `caution` 알림(GitHub `CAUTION`은 리치오 위험에 쓴다).
- 목록 번호 스타일.
- 고정 번호와 번호 숨김의 키.
- 표 주석.
- 여러 줄 수식의 라벨. Quarto의 `$$ … $$ {#eq-x}`는 remark-math·markdown-rs가 문서 끝까지 수식으로 읽는다.

퍼징의 그 밖의 차이 395문서와 거부 83문서는 원문 위치로 글자를 다시 자르는 후처리 구현의 결함이었다. 관례 후처리는 깨지기 쉽다.

쓰기에서 기존 라이브러리 문제를 찾았다. mdast-util-directive의 `:` 이스케이프 누락과 라벨 안 이스케이프 누락, micromark-extension-directive가 이름 안 탭을 받는 문제, to-markdown이 붙은 순서 목록의 구분자를 바꾸는 문제, 빈 체크 항목을 쓰지 않는 문제다. 모두 어댑터에서 우회했다.

저장소 `.md` 217개 중 새 읽기는 187개를 받아들였다(Core는 표식을 붙여 186개). 일반 마크다운 문제를 새 형식이 풀지는 않는다.

### 질문 2. 속도 (JS, 한 번 처리, 2,300 / 5,000블록 혼합, ms)

| 단계 | MyST(Core) | remark |
| --- | --- | --- |
| 파서 | 126 / 324 | 165~180 / 391~440 |
| 쓰기 | 295 / 695 (다시 읽기 검증 포함) | 48 / 108 |
| 같은 검증을 넣은 쓰기 | 위와 같음 | 247~259 / 572~584 |

remark 파서가 1.2~1.4배 느리고, 쓰기는 검증까지 포함하면 비슷하다.

### 질문 3. markdown-rs 일치

| 문서 | 구조 일치 |
| --- | --- |
| external 형식 | 1,024개 중 1,023 |
| directive 형식 | 1,028개 중 791 (차이는 모두 지시문. **markdown-rs에는 지시문이 없다**) |
| 저장소 `.md` | 217개 중 208 |

- markdown-rs 1.0.0은 `# #foo`의 첫 `#`를 버린다(CommonMark와 다름).
- 표 바로 다음의 `#…` 줄을 remark와 다르게 읽는다.
- 위치 규칙이 다르다. JS는 UTF-16, Rust는 바이트이고, 목록 끝·이스케이프로 시작하는 텍스트의 위치도 다르다. 원문 위치에 기대는 후처리를 Rust로 옮길 때 이 차이를 처리해야 한다.

### 4단계. Rust 부분 파이프라인 (ms, 2,300 / 5,000블록)

| 경로 | 읽기 | 의미 변환 | 쓰기 | 검증 포함 쓰기 |
| --- | --- | --- | --- | --- |
| ① MyST(Core, JS) | 327 / 736 | 20 / 42 | 1,116 / 2,563 (검증 포함) | 같음 |
| ② remark(JS) | 506 / 1,344 | 21 / 40 | 259 / 601 | 868 / 2,151 |
| ③ Rust 실행 파일 | 350 / 1,431 | 3 / 17 | 65 / 145 | 399 / 1,557 |
| ④ Node에서 WASM | 300 / 1,271 | 14 / 32 | 89 / 190 | 408 / 1,450 |

- 출력 Markdown은 ②와 ③, ②와 ④가 두 크기 모두 바이트 단위로 같았고, 의미 모델은 ①~④가 모두 같았다.
- Rust의 이득은 쓰기(remark의 약 1/4)와 의미 변환에 있다. 읽기는 MyST(markdown-it)보다 빠르지 않다.
- markdown-rs는 5,000블록에서 크기 2.2배에 시간 4.1배로 늘었다. 원인은 조사하지 않았다.
- 읽기·변환·검증 포함 쓰기 합계는 다음과 같다.
  - 2,300블록: ① 1.46초, ④ 0.72초
  - 5,000블록: ① 3.34초, ④ 2.75초
- 지금 저장 지연(2,300블록에서 2~5.5초)의 큰 부분은 반복 파싱·복제이고, #1983에서 다룬다. 위 값은 한 번 처리 기준이다.

**검증하지 않은 것**

- 새 읽기는 Core 수용 규칙(머리말 키, 라벨·인용 키, 유니코드, 고정 번호 모순)을 옮기지 않았다.
- 대소문자만 다른 각주 라벨은 시험하지 않았다.
- 마지막 측정 뒤에 external 후처리 결함 하나를 고쳤지만, 퍼징 10,000건은 다시 돌리지 않았다.
- Rust 쓰기 이식은 강조 기호 재선택(guess/fix)을 빼서 코퍼스 밖 입력에서는 바이트가 다를 수 있다.
- 편집기·CLI·Host·플러그인은 실행하지 않았다.
- MSVC 빌드 도구가 없어 GNU 툴체인으로만 빌드했다.

## 현재 결정과 어긋나는 점

스파이크는 Core를 바꾸지 않았다. 전환한다면 다음이 바뀐다.

- [ADR-0006](../adr/0006-native-document-boundary.md)과 [문서 지원 계약](../design/document-support-v1.md): 표식, 지원 문법, 정규 표기.
- [ADR-0023](../adr/0023-table-inline-breaks-and-notes.md)·[ADR-0024](../adr/0024-complex-tables.md): `{table}` 지시문의 표 주석과 `data-myst` span.
- [ADR-0008](../adr/0008-citations-and-bibliography.md): external 프로필에서 인용 역할 손실.
- 상호참조·번호·각주·그림·표 캡션 계약.
- [파서 보안 계약](../design/parser-security-v1.md)과 [의존성 패치](../contributing/dependency-patches.md).

[ADR-0002](../adr/0002-document-persistence-semantic-ownership.md)는 MyST를 영구 모델로 고정하지 않으므로 교체 자체와는 어긋나지 않는다. 2026-11-20 조사의 "MyST 유지" 결론과는 다른 선택지를 잰 것이다.

## 결론/후속

**미정.** 정해져야 할 것은 두 가지다. 첫째, MyST를 걷어낼 이유가 속도인지, 유지비(파서 업그레이드 대기, 패치 6개)인지, 외부 도구 호환인지다. 둘째, external 관례의 한계를 받아들일지다.

에이전트 추천은 다음과 같다.

- 속도만으로는 전환하지 않는다.
- 다른 이유로 걷어낸다면 섞는다. 1:1로 담기는 외부 관례(GFM, `$` 수식, `<sub>`·`<sup>`, Mermaid, alerts 5종, YAML)는 그대로 쓴다. 그림·표 구역, 상호참조, 인용, 목록 스타일, 대상은 리치오 표기로 둔다.
- Rust는 지금 전환의 근거가 되지 않는다.

전환 비용:

- Core MyST 경계 3,741줄 재작성. 경계를 가져오는 Core 파일 11개, `myst-*`를 직접 쓰는 파일 13개, #1983 국소 쓰기를 다시 맞춰야 한다.
- 테스트의 MyST 문법 약 314줄, 픽스처 34개, 바이트 회귀 데이터.
- 비서 스킬 예시 1곳, 샘플·기본 문서·템플릿.
- ADR·계약 문서.
- 편집기·CLI·SDK는 Core 모델만 써서 영향이 작다.

단계는 다음 순서를 제안한다.

1. 프로필과 표식 버전을 정한다.
2. 새 읽기·쓰기를 MyST와 나란히 두고 대조한다.
3. 정규 쓰기를 바꾼다.
4. 문서·샘플을 고친다.
5. MyST를 제거한다.

규모는 Core 경계만 수 주로 본다.
