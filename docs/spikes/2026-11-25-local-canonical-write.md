# 큰 문서의 국소 정규 쓰기 (#1983)

- Status: Historical
- Last verified: 2026-11-25, Windows, Node 24.22.3.
- Scope: 승인된 정규 원문과 바이트 범위 지도를 재사용하는 Core 쓰기 실험. 합성 문서, Core 픽스처, 공개 PDF 변환본을 사용했다.

## 목적

이미 전체 정규 쓰기를 통과한 문서에서 최상위 블록 하나를 고칠 때, 기존 작성기로 그 블록만 쓰고 양옆 블록을 다시 읽어도 전체 정규 쓰기와 승인·거부, 바이트, 의미 및 블록 경계가 같은지 확인한다. 적용 범위와 비용을 재서 [#1983](https://github.com/litzio/litzio/issues/1983)의 두 번째 단계를 판단할 근거를 만든다.

## 무엇을 만들었나

Core의 정규 출력이 한 번 더 써도 같고 **첫 직렬화 시도**만으로 유효한 경우에 국소 경로를 열었다. 기존 파서 줄 위치를 UTF-8 바이트 범위로 바꾸고 앞뒤 줄바꿈과 의미 지문을 기록했다. 표·그림·수식·알림 지시문은 MyST가 자식으로 펼칠 때 바깥 위치를 잃었다. 변환 직전 부모의 위치를 단일 자식 객체에 이어 주니 문서 전체를 다시 파싱하는 범위 구축은 가능했다. 쓰기 단계에 새 범위 기록기를 추가할 필요는 확인되지 않았다. 여러 자식으로 풀리거나 위치·구분자를 확인할 수 없으면 전체 경로를 쓴다.

같은 Core 연산을 블록 하나에 적용하고 첫 시도의 기존 작성기로 쓴다. 후보를 끼운 국소 창은 고친 블록과 존재하는 양쪽 이웃이다. 이 창을 네이티브 MyST로 다시 읽고 세 블록의 실제 바이트 범위와 의도한 의미 지문을 비교한다. 통과하면 뒤쪽 범위를 바이트 차이만큼 옮기고 전체 원문과 revision을 만든다. 위치가 갱신된 지도는 승인된 원문 한 버전에만 유효하다. 원래 모델에 있던 줄 위치는 다음 편집의 범위로 재사용하지 않는다.

대조군에는 같은 편집의 Core 연산과 전체 정규 쓰기를 모두 실행했다. 결과 전체를 다시 읽은 모델의 의미와 블록 순서를 국소 모델과 비교했고, 전체 작성기의 두 번째 출력까지 동일해야 통과로 셌다. 미주 호출 삭제 및 내용 축소 사례에는 Host의 미주 재조정도 적용했다. 각 추가 유형은 그 시점의 누적 허용 규칙으로 대조했다. 합성 문서 앞 20건씩과 픽스처·PDF 변환본 6,888건에는 각 단계의 규칙을 다시 실행했고 모든 단계에서 허용 불일치는 0건이었다. 편집 하나씩을 원래 정규본에서 시험하는 대조에 더해 52회 연속 편집에서 매번 새로 읽은 범위 지도와 갱신된 지도를 비교했다.

## 결과·관찰

### 입력과 대조

합성 문서 300·2,300블록에는 문단 65%, 1~3단계 제목 10%, 목록·10행 표·수식·그림 참조·미주 정의 각 5%를 넣었다. 문단 약 5%에 내부 링크와 미주 호출을 넣되 일부에 둘 이상의 호출을 배치했다. 모든 최상위 본문 블록에 두 가지 이상 편집을 만들었다. 기계 편집 시드 1983과 검수 편집 시드 19831125를 사용했다. 말미·중간·길이 변경과 이스케이프, 줄 시작 구문, 공백, 한글과 이모지, 매우 긴 글자, 미주, 링크, 마크와 수식을 포함했다.

직접 보관된 Core Markdown 픽스처 5개, Core 바이트 회귀 데이터의 보관 입력, 별도 반례 문서를 읽었다. 원래 네이티브 표식이 없는 픽스처에는 시험용 표식을 앞에 붙였다. 대조 입력 43개 중 1개는 전체 네이티브 쓰기가 거부했다. 나머지 입력에서 최상위 본문 전부의 범위를 찾았다. 공개 LSR 1.1 합성 PDF는 플러그인의 추출·변환·작성 입력과 Core의 `authorDocument`로 다시 생성했다. 권장 제외는 1쪽이었고 출력은 87블록 12,441바이트다. 이미지 파일 6개는 상대 경로만 사용했다. [공개 표본 안내](https://github.com/litzio/plugins/blob/0f06da6f2ad5760af14431ec02d55b612d86bdc2/plugins/document-import/pdf/test/fixtures/README.md)

### 적격 조건과 코드 근거

| 조건 | 전체 경로로 가는 이유 |
| --- | --- |
| 같은 최상위 블록 하나, 범위·양쪽 경계 확인 | 삽입·삭제·이동·종류 변경은 재생에서 경로와 블록 경계를 바꾼다. 파일 revision, 열기 기준과 편집 위치는 [편집 세션 저장 계약](../design/editing-session-save-v1.md) 및 [ADR-0003](../adr/0003-document-addressing-identity-boundary.md)에 따라 별도로 검증한다. |
| 한 줄 본문 글자, 제한된 마크·수식·일반 HTTPS 링크 | `serialize.ts`의 첫 출력으로 충분해야 한다. 여러 줄, 미확정 인라인 문법, 링크 정의·이름표와 미주 모양을 전체 경로로 보낸다. 참조 정의가 바뀌면 창 밖의 같은 이름 링크도 다르게 파싱될 수 있다. |
| 미주가 들어 있거나 미주를 만드는 편집 제외 | `footnote.ts`의 `endnotePlacement`와 `operations.ts`의 `reconcileEndnotes`는 호출에 따라 문서 끝의 정의를 재배치하거나 삭제한다. 마지막 호출을 지우는 다섯 블록 예에서 창이 통과해도 전체 저장은 먼 정의를 지웠다. |
| 표 칸 글자·수식과 캡션, 그림 캡션 | 표는 `tableOf`와 `assertStableTable`이 다루는 표 전체를 한 블록으로 쓴다. 격자·옵션·고정 번호·레이블은 그대로다. 그림은 캡션만 바꾼다. 줄바꿈과 지시문 경계가 달라지거나 주변 의미가 달라지면 전체 경로를 쓴다. |
| 제목 글자의 제한된 변경 | `headingLabelTransform`은 제목 글자에서 암시적 ID를 만들고 앞의 목표 레이블이 다른 노드에 연결될 수도 있다. 수준·레이블과 정규화한 이름이 같으며 내부 참조가 없는 문서의 일반 글자 변경만 열었다. 제목을 보통 새 단어로 바꾸는 편집과 frontmatter·번호 변경은 전체 경로다. |
| 목록 항목 글자, 한 줄 블록 수식, 단순 알림 상자 글자 | 목록과 인접한 블록 및 서로 붙은 목록은 전체 경로로 보낸다. 목록의 느슨함과 블록 합치기는 주변 파싱에 영향을 준다. 수식은 한 줄 LaTeX의 일부 문자와 기존 경계를 유지할 때만 열고 알림 상자는 단순 본문만 바꾼다. |
| 다시 쓰기 시 첫 시도 유지 | `serialize.ts`의 마크 경계 및 줄 시작 이스케이프 재시도는 문서 전체를 다시 만들 수 있다. 기준 문서가 대체 시도를 쓰거나 새 블록이 첫 시도에서 거절되면 전체 경로를 사용한다. |

시작 시 범위 구축에는 전체 승인·안정성·첫 시도 확인과 위치 보존 파싱이 들어 있다. 매 승인마다 범위 지도에서 뒤쪽 항목을 옮기는 비용은 뒤 블록 수에 비례한다. 원문 결합과 revision 해시는 전체 바이트에 비례한다. 지도와 모델의 크기는 V8 직렬화 바이트다. 실제 힙 크기, 소스 진단용으로 잡고 있는 문자열, 일시 복제물은 포함하지 않는다.

## 현재 결정과 어긋나는 점

비교 후보가 파싱하는 범위는 창의 블록이다. 현재 [ADR-0002](../adr/0002-document-persistence-semantic-ownership.md), [ADR-0006](../adr/0006-native-document-boundary.md), [정규 쓰기 계약](../design/document-support-v1.md#canonical-output-and-compatibility)이 요구하는 전체를 저장 전 다시 읽는 보호와 동등하다고 판정할 근거는 부족하다. 대조는 관측된 표본에서 조건과 함께 근거를 제공한다. 플러그인 입력·MyST 임의 문법·창보다 멀리 전파되는 모든 효과, 실제 업무 편집 분포, HTTP와 브라우저 지연, 파일 충돌 및 다중 세션은 시험하지 않았다. 후보는 스파이크 브랜치에서만 실행했다.

## 결론/후속

**미정.** 먼저 #1983의 1단계를 권한다. Host가 직접 승인한 원문·편집·결과 revision을 재사용하면 보호를 유지하면서 중복 검사를 줄일 수 있다. 국소 쓰기를 검토할 때는 본문 한 줄 문단과 표 칸 글자·인라인 수식으로 시작하고, 동일 요청의 전체 검증을 저장 전 판정으로 유지하는 병행 대조를 먼저 운영한다. 전체 검증을 주기적으로 돌려 어긋난 문서의 빠른 경로를 끄는 장치는 상시 병행 대조 이후의 탐지 보강이다. 전체 검증을 저장 뒤로 미루면 발견 전 잘못된 원문이 이미 쓰일 수 있으므로 지금의 저장 전 보호가 약해진다.

제품에 넣는다면 Core가 범위와 의미 조건, 국소 직렬화와 확인을 소유한다. Host는 승인 revision·열기 기준·누적 편집을 검증해 승인 모델에서 한 블록에 해당하는 변경을 얻고, 교체 직전 기존 revision 검사를 수행한다. 현재 요청은 열기 원문 기준의 누적 편집을 보내므로 검증된 승인 상태 대비 실제 변경을 Host가 산출하거나 revision에 묶인 변경 계약이 필요하다. Undo·Redo와 저장 중 입력의 합성을 유지해야 한다. SDK의 `writeDocument`는 문서 전체와 기대 revision을 받는다. 신뢰할 승인 스냅샷과 Core가 확인할 수 있는 편집 내역이 확보될 때 같은 Core 경로를 공유할 수 있다.
