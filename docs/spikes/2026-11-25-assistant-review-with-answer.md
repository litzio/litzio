# 정답을 제공한 비서의 변환 문서 수정

- Status: Historical
- Last verified: 2026-11-25, Windows 격리 Host에서 공개 LSR 1.1 합성 표본 반영 및 저장본 확인.
- Scope: 13쪽 PDF와 고정 변환본 하나, Codex 두 모델, 입력 조건별 한 턴 한 회.

## 목적

비서에게 틀린 곳과 목표 형태를 제시하면 원래 맞던 내용을 보존하면서 저장본을 111/111까지 고칠 수 있는지 확인했다. 사람이 고칠 곳을 골라 작성한 목록과 원본 작성자가 정의한 정답 JSON을 함께 비교했다.

## 무엇을 만들었나

[변환 문서 검수](2026-11-25-assistant-review-converted-document.md)와 [낮은 추론 강도](2026-11-25-assistant-review-low-effort.md)의 변환본, 채점기, 111요소 및 기준 오류 14묶음을 재사용했다. 플러그인 커밋 `7f162d0e`에서 동일한 PDF 해시와 변환본 revision을 재현했다. 기준은 80/111이다.

- **A — 고칠 곳 목록.** 첫 문장은 “정답지에 없는 곳은 지금 문서가 맞다”였다. PDF 쪽, 현재 문서의 글자나 캡션, 목표 구조와 정확한 내용을 적었다. 예를 들어 원본 PDF 3쪽의 독립 문단 `Review participants`는 글자를 유지하고 H3로 바꾸도록 했다. 표 셀 수식은 어느 행·열에 넣을지와 LaTeX를, 두 Route 표는 칸 값·캡션·주석 문장을 제시했다.
- **B — 원래 정답 JSON.** 픽스처의 `standards.json`을 원본 바이트 그대로, 형식 설명이 있는 `README.md`와 함께 제공했다. 물리 1쪽, 병합 셀, PDF 좌표와 관계까지 포함된 자료다. 이 조건의 비서에게 채점기의 제외 범위나 리치오 표현에 맞춘 규칙은 제공하지 않았다.

A 목록대로 별도 사본을 직접 수정해 **111/111**, 기존 정답 손상 0, 기준 밖 블록 0, 공식 `check` 유효를 유료 실행 전에 확인했다. K.2 그림의 축 제목·눈금까지 들어간 교체 이미지를 PDF와 눈으로 맞춰 확인한 뒤 기존 수동 판정표에 그 이미지 해시를 등록했다. 같은 방식으로 실행 결과의 새 그림을 판정했다. 확인본은 채점 직후 삭제했다.

각 대화는 새 Host와 새 사본에서 전체 접근, 15분 제한과 승인 미응답으로 실행했다. 활성 문서 경로는 Host가 전달했다. 요청은 해당 조건의 정답 파일에 맞춰 문서를 고치고 이미 맞는 곳을 건드리지 말라는 한 턴이었다. 채점기와 기준 오류 자료는 열린 폴더에서 제외했다. B를 먼저 실행한 뒤 A 목록을 다시 생성해 A를 실행했다.

### 방법·도구·시간

| 회차 | 초 | 도구 호출 | 응답 수 | 합계 토큰 | 마지막 맥락 | 저장 방식 |

Codex CLI 0.172.0 세션의 `turn_context`에서 Terra `high`, Sol `medium`을 직접 확인했다. 토큰 합은 사용량과 응답 ID가 함께 기록된 응답의 합계이며 캐시 입력을 포함한다. 과금액이나 엔진 내부 재시도 수는 확인하지 못했다. 승인 요청은 0건이다. 카탈로그 사전 점검 1회와 A Sol의 제출 전 Host 연결 실패 1건에는 유료 턴이 없었다. A Sol은 새 Host에서 허용된 한 번의 재시도로 완료했다. 네 모델·조건 조합을 합쳐 실제 유료 대화는 네 개, 각각 한 턴이었다.

- **A Terra**는 공식 `read_document`로 정답지와 저장본을 읽고, CLI 도움말을 확인한 뒤 PyMuPDF로 그림을 잘라 Python으로 문서를 저장했다. 끝에는 `check`를 호출했다. 열린 폴더 밖의 로컬 메모리 검색 결과와 격리 Host의 작업 디렉터리 목록을 확인했다.
- **A Sol**은 공용 PDF 스킬, 정답지, Markdown을 읽고 제품 문서·fixture에서 표 주석과 수식 표기를 확인했다. Poppler로 그림을 자르고 Markdown 패치 두 번, 자산 복사, `check`·`inspect`를 수행했다. 공용 스킬과 제품 checkout은 열린 폴더 밖이었다.
- **B Terra**는 `read_document`로 저장본을 읽었다. 처음에는 변환 문서 하위 폴더에서 JSON을 찾지 못했고, 상위 입력 폴더에서 찾아 전체를 읽은 뒤 Node로 본문·표 셀·식 일부를 추렸다. 저장은 정답 JSON에서 가져온 요소와 고정 문자열 치환을 결합한 Node 스크립트 한 번이었다. 이후 `check`, PDF 해시, 본문 문자열 대조를 실행했다. 열린 폴더 밖에 있는 격리 작업 디렉터리 목록을 읽었다.
- **B Sol**은 `read_document`와 `inspect`를 사용하고 JSON의 본문 역할·순서·관계와 표의 행·열·범위, 페이지 좌표를 별도로 추출했다. CLI 미리보기와 임시 후보 문서를 검사하고 원본 10쪽을 Poppler로 다시 자른 뒤 패치했다. 공용 PDF 스킬과 격리 작업 디렉터리의 리치오 스킬·CLI를 참고했다. 원래 자료에 있는 물리 1쪽의 표지·목차도 B의 원본 요소에 맞춰 추가했다. B Terra 역시 물리 1쪽 내용을 추가했다.

네 대화가 폴더 밖의 로컬 메모리를 검색했다. A Terra에서만 일치 결과를 반환했다. 관찰된 호출에는 앞 실험 결과, 현재 채점기, 기준 오류 파일 또는 다른 조건의 정답지를 읽은 기록이 없다. 전체 접근은 화면에 보이는 입력 폴더 밖을 읽을 수 있다. 정리한 도구 순서와 상태를 회차별 결과에 보존했다. [도구 기록](https://github.com/litzio/litzio/blob/dc4890c1a6872cc5e42b3a80a40e61ba6d531bd9/scripts/spike-assistant-review/results.json)

## 현재 결정과 어긋나는 점

없음. 활성 문서 경로와 직접 수정은 [범용 비서 ADR](../adr/0021-general-agent-assistant.md)을 따랐다. 표 자체 주석을 지원하는 [현재 계약](../design/document-support-v1.md)과 고정 채점기의 주석 위치 기준에는 차이가 있다.

## 결론/후속

**미정. 사람이 편집 범위와 목표 구조를 지정하고 저장 후 해당 구조를 확인하는 방식을 다른 표본과 반복 실행으로 검증할 것을 추천한다.** A에서 Terra는 111점, Sol은 109점이었다. 둘 다 원래 맞던 80개를 보존했다. B는 각각 106점, 102점이었다. B Sol에서 동일한 문장을 표 주석으로 옮긴 다섯 건이 고정 기준에서 감점됐다. B가 제공한 자료를 두 모델 모두 읽고 활용했지만, 범위와 표현을 직접 결정했다. 두 모델 모두 평가에서 빠진 물리 1쪽을 복원했다. Sol은 병합 범위의 수식 복제와 H2를 남겼고 Terra는 3개 수식의 저장 종류와 그림 교체를 남겼다.

앞의 18회에서 놓쳤던 참가자 H3가 이번 네 회에서는 맞았다. 부록 M H2도 A 두 회에서 맞았고 B 두 회에서 남았다. 이 항목들은 목표 형태를 알려 주었을 때 실행할 수 있었다. A Sol의 주석 형식 선택과 B Terra의 인라인 수식은 위치와 값을 알아도 저장 구조를 따로 확인해야 하는 사례다. 현재 Host가 선택 가능한 표 주석 형식을 추가했기 때문에, A Sol의 두 감점을 편집 수단 부재의 증거로 볼 수 없다.

1. 기존 `check`에 더해 목표 구조를 확인할 수 있어야 한다. B Terra의 인라인 수식과 B Sol의 빈 복제 칸은 유효성 검사에서 둘 다 통과했다.
2. 편집 대상 밖의 의미 차이를 검토하기 쉬워야 한다. B Sol은 기준 오류 밖 43개 블록을 바꾸고 주석 다섯 건을 다른 구조로 옮겼다. `inspect`의 표 주석 내용을 함께 읽어야 보존된 문장과 저장 위치 변화를 구분할 수 있었다.

한 PC, 한 합성 표본, 모델과 조건마다 한 번이다. 비교 대상은 두 턴이었고 이번은 한 턴이다. B가 먼저 실행됐고 모델 간 실행은 일부 겹쳤다. 최신 Host의 지원 형식과 고정 채점기가 다르므로 관찰된 차이를 정답지 형식 하나의 효과로 일반화할 수 없다. 원본 대응의 재연결과 다른 문서의 재현성은 확인하지 않았다.
